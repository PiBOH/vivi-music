## Phase 2 — Sync: queue + playback position
- [x] Capture the queue and position from the Android player (`pushPlayback` is wired from MusicService on track/play changes).
- [x] Resume on desktop: apply `pendingPlayback`; the desktop also pushes its playback and applies incoming snapshots (bidirectional), with echo suppression.
- [x] Precise sync: seek is pushed instantly (both sides), same-track commands apply as a lightweight in-place seek (no restart), and positions carry a timestamp (`positionAtMs`) so receivers extrapolate while playing; PING/PONG clock-sync (relay + `server.js`) removes clock skew between phone and PC.
- [x] Drift auto-correction: while playing, the position is re-pushed every 5s (`SyncServer.RESYNC_TICK_MS`) so players re-align continuously; a 1 s tolerance (`RESYNC_TOLERANCE_MS`, raised from 250 ms in DE 1.33.110 / APK 6.4.38) skips near-no-op seeks to avoid audio glitches. Explicit user seeks are now flagged (`PlaybackSnapshot.userSeek`) and applied exactly on the peer (both directions), while periodic drift-ticks only catch up FORWARD — so the leader device is never dragged back by the follower's stale position (this fixed the visible seekbar "jump back").
- [x] Resolving/buffering handshake: `PlaybackSnapshot.isResolving` is set by the desktop while it resolves/downloads (until the first position report = audio actually flowing) and by the mobile while ExoPlayer is `STATE_BUFFERING`. The receiver prepares the queue but holds playback (and `effectivePosition` stops extrapolating a frozen position), so neither device starts a track ahead of the other while the peer is still resolving. Mobile pushes the buffering→ready transition promptly (not just on the 5s tick). Resolving transitions bypass the echo-suppression window on both sides (they were being swallowed by the 1.5s window right after applying a remote snapshot, so a phone-initiated track change played ahead of the still-resolving desktop). The desktop no longer `startPaused`-holds on the peer's resolving state (it is the slower device and the phone holds for it), and it ignores the peer's play/pause echoes while it is itself resolving — this fixed a startup deadlock where both paused and the desktop stayed silent (in the mixer but emitting nothing). DE 1.33.110: the desktop holds again when the PHONE is still resolving (symmetric wait), but auto-resumes the moment its own stream is ready (`resumeWhenReady`) instead of emitting a transient `isPlaying=false` snapshot that paused the phone — so a phone-initiated track change no longer plays the desktop ahead/behind with a jump. A seek/play-pause received while the desktop was still resolving its own stream was dropped (its own resolution decides when audio starts) and only recovered on the next 5s re-sync tick; the latest peer snapshot is now re-applied the moment the desktop's stream finishes resolving (`Main.kt` re-apply effect on `isResolving` true→false), so seek/play-pause follows the phone even over a slow phone hotspot where resolution takes longer. DE 1.33.101 / APK 6.4.29: a mid-song rebuffer no longer pauses the paired device — a same-track `isResolving` now only skips the stale-position seek and keeps playing (initial resolution still holds the peer), fixing the "freezes randomly while paired" bug. DE 1.35.2: the re-apply-after-resolving effect now only honors a snapshot that arrived WHILE the desktop was actually buffering (receivedAt >= resolvingSince), so a stale pre-play snapshot can't pause a track the user just started; and a periodic peer tick older than a full sync tick (5 s) with `isPlaying=false` is ignored, so the desktop can't auto-pause a few seconds after play because the phone's snapshot hasn't caught up — pressing play once is enough again even over a slow hotspot.
- [x] Position-sync jump-back fixed: the relay clock offset used for position extrapolation was measured only 25 s after connect (slow EMA convergence), so right after pairing the two devices extrapolated from raw local clocks and kept seeking each other back/forth by the clock skew. The first PING now fires immediately on connect, the first PONG sets the offset directly (no EMA), and `positionAtMs` is only stamped once the offset is known (otherwise the raw position is used, so older relays don't skew-corrupt the extrapolation).
- [x] Volume sync (two channels): the in-app player volume (`volume`) mirrors the mobile/desktop slider pixel-for-pixel, and the native OS system volume (`systemVolume`) mirrors Android STREAM_MUSIC <-> desktop OS volume (WinMM on Windows, `pactl`/`amixer` on Linux, `osascript` on macOS — all best-effort). The in-app volume channel can now be disabled independently with the "Sync VIVI volume" toggle (Settings → Devices and Settings → Player & audio on both editions); the native OS volume sync stays separate and unaffected. Both sides poll volume (700ms mobile / 500+800ms desktop) with per-field echo guards and **retry on a dropped push** (a push that lands in the echo-suppression window is re-sent on the next tick instead of being lost), so volume syncs reliably even while idle. Windows now drives the **master** volume through WASAPI `IAudioEndpointVolume` (Core Audio COM marshaled onto a dedicated MTA thread) and pins the app's own session (`VIVIMusic` in the mixer) to 100% — WinMM `waveOut*` only moved the per-app session volume, so it was replaced; every native call is guarded against missing symbols. The "Sync VIVI volume" toggle itself is now part of the shared settings snapshot (read/pushed/apply on both editions), so flipping it on one device mirrors on the other. DE 1.35.3: the EXPRESSIVE player design's volume slider had an empty `onValueChange = { /* Volume update */ }` placeholder from the UI port — dragging it did nothing, even unpaired; now wired to the real handler. A track that finished kept its end position, so pressing play restarted from the end and instantly "completed" again; `startCurrent` now restarts finished tracks from 0:00. DE 1.35.2: a local drag on the VIVI volume slider now wins for 2 s over any incoming remote value, so an echoed or stale volume from the phone can't snap the slider back the moment the user lets go (previously the peer kept re-applying its own value and the slider appeared stuck).
- [x] Paired device names shown on both sides (desktop announces its real hostname, mobile shows the paired desktop name and vice versa).
- [x] Play/pause button stuck on "play" while audio kept playing (DE 1.33.112): the player position callback re-applied the initial `resumeWhenReady` intent as `isPlaying` on every ~100 ms report, overwriting a later manual play/pause toggle (e.g. after the phone started a track paused/resolving). The intent now applies only on the resolving→ready transition; later reports only advance the position.

- [x] Settings persistence is atomic: `DesktopSettings` exposes a synchronized `update(transform)` (read-modify-write) and every call site now uses it instead of `save(load().copy(…))`, so a UI-thread setting change (e.g. notification mode) can't be lost by a concurrent device-sync save.
- [x] DE 1.37.1: paired "must press play twice" fixed via 3s grace window after a local play/navigation command (peer pre-action paused echo ignored); manual "next" at queue end wraps to the first track.
- [x] DE 1.37.2: native title bar toggle no longer crashes (window chrome frozen at startup; setUndecorated is never called on a displayed frame); closing while maximized persists the floating restore bounds instead of the full-screen ones, so the window no longer reopens stretched over the Windows taskbar (restore also clamps to the last monitor's work area).
